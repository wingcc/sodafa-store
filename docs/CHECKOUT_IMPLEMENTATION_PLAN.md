# Checkout, Customers, Orders & Delivery — Implementation Plan

> **Status:** Planning / Analysis complete. **No implementation yet.**
> Generated after inspecting `supabase/migrations/*`, seed data, API routes, repositories, UI state, auth, and toast system.

---

## A. Architecture Analysis — How the current Checkout → Order → Customer flow works

### What actually exists today (the gap)
The current `app/checkout/components/CheckoutClient.tsx` **does not create a real order in the database**. Its `handleConfirmOrder()` flow is:

1. Calls local `validate()` (name/phone/address only — no email, no delivery selection, no coupon).
2. Builds an in-memory `orderData` object (`orderNumber = "SODFA-XXXXX"` generated client-side, `cartTotal`, hard-coded `shipping = 35 or 0`, `grandTotal`).
3. `localStorage.setItem('last_sodfa_order', JSON.stringify(orderData))`.
4. `setTimeout(..., 1000)` — a fake "placing" delay.
5. `clearCart()` + `router.push('/order-confirmation')`.

`app/order-confirmation/components/OrderConfirmationClient.tsx` only **reads from `localStorage`** (`last_sodfa_order`); if absent it shows hard-coded fallback mock data. **No DB write, no customer write, no order write, no confirmation page DB fetch.**

So today Checkout → Order Confirmation is a **simulated** flow. The "Orders API" (`POST /api/orders`) exists but is **unreachable from the checkout** and is itself broken (see Risks).

### Data layers present
- **Cart state**: `app/contexts/UIContext.tsx` (`useUI`) — in-memory React context, **not** persisted to localStorage. Shape: `CartItem = { id, name, price, qty, image }`. `cartTotal = Σ(price × qty)`. `clearCart()` empties it. `id` is the product's `id` (string) (see `ProductCard` → `onAddToCart(product.id)`, and `useProducts` maps `id: String(row.id)`).
- **Auth**: `app/contexts/AuthContext.tsx` — optional Supabase Auth session (`useAuth`). The public store/checkout is **not protected** by `middleware.ts` (only `/dashboard` and `/api/admin` are protected). So **guest / Cash-on-Delivery checkout is the intended, unauthenticated flow**; there is no login requirement.
- **Supabase clients**:
  - `lib/supabase/client.ts` → `createClient()` — **anon key**, browser.
  - `lib/supabase/server.ts` → `createServerClient()` — **anon key**, server-side.
  - `lib/supabase/admin.ts` → `createAdminClient()` — **service-role key**, server-only (bypasses RLS). **Intentionally NOT exported from `lib/supabase/index.ts`** to prevent client-side use.
- **DB layer**: `lib/db/repositories/*` (Customer, Order, OrderItem, Shipping, Coupon, Product, Category, Notification, Admin, Settings).
- **API layer**: `app/api/*` route handlers using the standard `successResponse / errorResponse / ... / toApiError` helpers (`lib/api/*`). Consistent `{ success, data | error }` JSON contract.
- **Toast**: `lib/toast/*` — `useToast()` → `addToast(type:'success'|'error'|'warning'|'info', message, options?)`. `ToastProvider` is mounted **globally** in `app/layout.tsx` (wrapping `<Providers>`), so it is available in `CheckoutClient` and `OrderConfirmationClient`.

## B. Database Analysis — Existing relevant tables & columns

### Tables that matter (from `001_initial_schema.sql` + `seed.sql`)

**`customers`** — `id PK uuid`, `name NOT NULL`, `email UNIQUE nullable`, `phone`, `avatar`, `total_orders`, `total_spent`, `currency`, `last_order_date`, `registered_at` (defaults NOW), `status`, `favorite_categories text[]`.
- ⚠️ Has **no `created_at`/`updated_at`** (uses `registered_at`).
- ⚠️ **No INSERT policy for anon/public** (only `SELECT/UPDATE WHERE auth.uid()=id` + admin). Guest checkout cannot write a customer via anon key.
- ✅ `email` is UNIQUE → usable as a dedup key.
- ✅ DB trigger `update_customer_stats` (AFTER INSERT/DELETE on `orders`) **auto-increments `total_orders`**, adds to `total_spent`, sets `last_order_date` (where `customers.id = NEW.customer_id`). So if we set `orders.customer_id` correctly, **customer stats are maintained automatically by the DB** — do NOT recompute them in the frontend.

**`customer_addresses`** — `id PK`, `customer_id FK`, `label`, `name`, `address`, `city`, `region`, `phone`, `is_default`, `created_at`. Has full address data.

**`orders`** — `id PK uuid`, `order_number UNIQUE` (auto-generated by DB trigger `generate_order_number_trigger` → `SDF-YYYYMMDD-<6hex>`), `customer_id FK nullable`, `customer_name/email/phone`, `subtotal`, `discount`, `shipping_cost`, `total`, `currency`, `payment_method` (enum, default `cash_on_delivery`), `payment_status` (default `pending`), `order_status` (default `pending`), `shipping_address JSONB`, `billing_address JSONB`, `tracking_number`, `shipping_provider`, `notes`, `created_at/updated_at`.
- ⚠️ **No `delivery_method` column** (only `shipping_cost`, `shipping_address`, `shipping_provider`). Needed to record Standard/Express.
- ⚠️ **No `coupon_code`/`coupon_id` column.** Only `discount` (decimal) exists. To "store the coupon with the order" we need a code column.
- ⚠️ **No INSERT policy for orders/order_items for anon/public.** `POST /api/orders` currently uses the anon `createServerClient()` → **RLS will block the insert**. Must use `createAdminClient()`.

**`order_items`** — `order_id FK`, `product_id FK`, `product_name`, `product_image`, `variant`, `quantity`, `unit_price`, `total`. All fields needed for order items exist.

**`order_timeline`** — `order_id`, `status`, `timestamp`, `note`. Seeded per order.

**`shipping_zones`** — `id PK`, `name`, `cities JSONB (array of plain English names e.g. ["Casablanca","Rabat",...])`, `created_at`. Public-read policy.

**`shipping_methods`** — `id PK`, `zone_id FK`, `name`, `price`, `estimated_days`, `free_shipping_threshold nullable`. Public-read. Seed: Zone1 Standard 25 MAD / Express 45 MAD; Zone2 Standard 35 / Express 60. Each zone's Standard has `free_shipping_threshold = 500`.

**`coupons`** — rich: `code UNIQUE`, `discount_type` ('percentage'|'fixed'), `discount_value`, `minimum_order`, `maximum_discount`, `applicable_to` ('all'|'products'|'categories'|'customers'), `applicable_ids text[]`, `start_date`, `end_date NOT NULL`, `usage_limit`, `used_count`, `customer_usage_limit`, `status` ('active'|'inactive'|'expired'), `created_at`. Public policy? **No SELECT policy for coupons** — only admin `FOR ALL`. So the public **cannot read coupons** via anon! The coupon repo /validate endpoint must use admin client. `increment_coupon_usage` RPC: ⚠️ **referenced by `CouponRepository.incrementUsage` but DOES NOT EXIST in any migration** (grep over `supabase/migrations` → 0 matches). Broken.

**`store_settings`** — has key/value; seeded with `free_shipping_threshold = '500'`. Public-read.

### City ↔ zone mapping problem
- Dropdown (`MOROCCAN_CITIES`) uses bilingual Arabic labels as the **value**, e.g. `"الدار البيضاء (Casablanca)"`.
- DB `shipping_zones.cities` stores **plain English** names, e.g. `"Casablanca"`.
- ⇒ The selected value never matches the DB city list. **Must normalize**: use plain English city name as the option `value` (display bilingual label), so a selected city can be matched against `shipping_zones.cities`. All 15 real cities in the dropdown map cleanly to seeded zones; `"مدينة أخرى (Other City)"` maps to none → no delivery options (must error gracefully).

### Conflicting "free shipping" thresholds
- `CartDrawer.tsx`: hard-coded `FREE_SHIPPING_THRESHOLD = 300` → free when cart ≥ 300, else `35 MAD`.
- `CheckoutClient.tsx`: `cartTotal >= 300 || cartTotal === 0 ? 0 : 35` (mirror of the same).
- `store_settings`: `free_shipping_threshold = '500'`.
- `shipping_methods.free_shipping_threshold`: `500` (per-method).
- ⇒ **Three different sources of truth** for the free-shipping rule and delivery price. The checkout must instead derive delivery price **from the selected city's shipping method** (DB), with free-shipping applied per-method's `free_shipping_threshold`.

## C. Implementation Plan — Logical Phases

### Phase 0 — Schema hardening (migration)  [do before wiring frontend]
Add the two missing order columns + the missing coupon-usage RPC/trigger, and reconcile free-shipping source of truth.
- Add `delivery_method VARCHAR(100)` (and optionally `delivery_method_id uuid`) to `orders`.
- Add `coupon_code VARCHAR(50)` to `orders` (nullable).
- Add `increment_coupon_usage(coupon_id uuid)` SQL function (atomic `used_count = used_count + 1` with `usage_limit` guard) — fixes the broken repo call.
- Optionally add a `coupon_usage` join table if per-customer usage tracking (`customer_usage_limit`) is needed (currently not enforced). Minimal plan: enforce `usage_limit`/`used_count` + `status` + dates; defer per-customer usage to a follow-up.
- Regenerate `lib/supabase/types.ts` (or hand-sync) so `OrderInsert`/`CouponRow` include the new columns.

### Phase 1 — Shared pricing + shipping service (single source of truth)
- Create `lib/utils/pricing.ts` (or `lib/server/pricing.ts`) exporting:
  - `calcSubtotal(items)` — `Σ unit_price × quantity` (decimal-safe rounding).
  - `calcDiscount(subtotal, coupon)` — percentage (capped by `maximum_discount`) vs fixed; respects `minimum_order`.
  - `calcFinalTotal({ subtotal, deliveryFee, discount })` — `subtotal + deliveryFee − discount`.
  - These are imported by the Checkout UI, the order-creation route, and the confirmation display.
- Create a server-only **shipping service** (`lib/server/shipping.ts`) with `getZoneForCity(zones, city)` (case-insensitive match of plain English city name against each zone's `cities` array) → `getMethodsForCity(city)` → returns the zone's methods with live prices; and `getDeliveryFee(method, subtotal)` honoring `method.free_shipping_threshold` and the global `store_settings.free_shipping_threshold`.

### Phase 2 — Backend: trusted checkout API (admin client, server-side revalidation)
Replace/extend the broken `POST /api/orders` with a dedicated, transactional **`POST /api/checkout`** (preferred, keeps the simple-orders route intact) that:
1. Validates input with a Zod schema (name, phone, email optional+email-format, address, city, deliveryMethodId, couponCode optional).
2. Server-side **validate coupon** against DB (active, date range, minimum_order, usage_limit, applicable scope) → compute discount. Revalidates the customer-supplied discount; **never trusts the frontend**.
3. Server-side **resolve delivery** (city → zone → method → price, with free-shipping rule) → `deliveryFee`. **Never hard-codes prices.**
4. Compute `subtotal`, `discount`, `deliveryFee`, `total` via the shared pricing util.
5. **Find-or-create customer** (admin client): by email if present (UPDATE existing `name/phone` but never duplicate; preserve stats — DB trigger handles increment); if no email, create a new customer row (guest) with a fresh `id`.
6. **Insert order** (admin client) with `payment_method='cash_on_delivery'`, `payment_status='pending'`, `order_status='pending'`, real DB-generated `order_number`, `customer_id`, full `shipping_address` JSONB, `delivery_method`, `coupon_code`, `subtotal/discount/shipping_cost/total`.
7. **Insert order_items** (admin client) for each cart line (`product_id` from cart `id`, `unit_price`, `quantity`, `total`, images).
8. **Increment coupon usage** via the new RPC.
9. Return `{ success, data: order }` (the full created order incl. `order_number`) — or roll back / not clear cart on failure. All errors surface as structured `errorResponse` (never silent).

### Phase 3 — Checkout UI (CheckoutClient.tsx)
- Add **Email** field (optional, validated only when filled, email format).
- Replace hard-coded city `<select>` with **dynamic loading** of `/api/shipping` zones; render plain-English city `value` with bilingual label; on city change → load methods + auto-select the cheapest/Standard.
- Render **delivery method list** (from DB) with names + prices; clicking one sets `deliveryMethod`.
- Add **Coupon Code** input + Apply button (calls `POST /api/coupons/validate` or reuses checkout validate) → shows applied discount, allows remove.
- Recalculate totals live via the shared pricing util: `Subtotal + DeliveryFee − Discount = Final Total`.
- `Confirm Order` → `POST /api/checkout` → on success: `clearCart()`, navigate to `/order-confirmation?orderId=<id>` (preferred) or write the returned order to `localStorage` (fallback to reuse existing confirmation component). On failure: **show toast, do NOT clear cart, do NOT navigate**.
- Use `useToast` for all errors; keep the Arabic/English `useLanguage` bilingual UI.

### Phase 4 — Order Confirmation (OrderConfirmationClient.tsx)
- Prefer reading the order **from the DB** by `orderId` (query param) so the displayed data always matches what was actually persisted. If a guest has no auth, fetch via a public/lookup endpoint or reuse the object passed back from the checkout API (store in `localStorage` as today's pattern, but populated from the real DB row).
- Show: real `order_number`, customer name/phone/email, city + address, chosen **delivery method + fee**, **applied coupon code + discount**, itemized items, `subtotal`, `discount`, `delivery`, `total`. All from the single pricing util.

### Phase 5 — Reconciliation & cleanup
- Remove hard-coded `300`/`35` shipping logic from `CartDrawer.tsx` and `CheckoutClient.tsx`; point both at the shipping service + settings.
- Remove the fake `setTimeout`/mock `orderNumber` generation; use DB-generated number.
- Keep the WhatsApp quick-order links as-is (they are a separate, manual backup channel).

## F. Risks / Existing Problems (must be addressed)

1. **RLS blocks guest checkout writes (CRITICAL).** `POST /api/orders` and `POST /api/customers` use the **anon** `createServerClient()`. `orders`, `order_items`, `customers` have **no INSERT policy for the public/anon role** (only SELECT by `auth.uid()` and admin `FOR ALL`). In a guest COD flow `auth.uid()` is null → inserts are rejected. **Fix: use `createAdminClient()` for all write operations.** This is the single biggest risk.

2. **Customer duplication risk.** `customers.email` is UNIQUE, so dedup by email is safe — but the flow is guest-based (no auth), so many guests will skip email. Without email we can't dedup, risking duplicate customer rows. **Mitigation:** primary dedup by email; for no-email guests create a new row but warn that phone-based dedup requires a normalized `phone` UNIQUE constraint (currently absent). Never `UPDATE` by `id` guessed from a form.

3. **Stats are DB-driven but fragile.** `update_customer_stats` trigger fires on `orders` INSERT and updates `customer_id`. If `orders.customer_id` is null or wrong, stats silently don't update. Ensure the order is created with the correct `customer_id` from step 6.

4. **Coupon security.** `POST /api/coupons` and the repo have **no server-side validation** for an arbitrary cart — the existing repo only `findByCode`/`incrementUsage`. The frontend must NOT compute the discount. All coupon validation + discount computation must happen server-side and the **same computed `discount`** must be written to the `orders.discount` column (and re-derived, not trusted from the client) at order creation.

5. **Broken coupon RPC.** `CouponRepository.incrementUsage` calls `rpc('increment_coupon_usage', ...)` but that function is **not defined in any migration** → always errors. Must add it (Phase 0.1).

6. **Pricing inconsistency.** Three hard-coded copies of the free-shipping rule (`CartDrawer` = 300/35, `CheckoutClient` = 300/35, `store_settings` = 500, `shipping_methods` = 500). **Must converge on the DB-driven shipping service + settings.** Risk: the confirmation page, cart drawer, and checkout show different totals.

7. **Order number mismatch.** Frontend generates `SODFA-XXXXX`; DB trigger generates `SDF-YYYYMMDD-<hex>`. The confirmation must use the **DB-generated** number returned from the create call.

8. **City label ↔ DB mismatch.** Dropdown values are bilingual Arabic strings; DB cities are plain English. Without normalization, zone lookup always fails → must fix (use plain-English `value`).

9. **Cart clearing on failure.** Must only `clearCart()` after a **successful** DB order insert. The current code clears inside a `setTimeout` regardless. Risk: network error → cart wiped + no order.

10. **"Other City"** is in the dropdown but has no zone → no delivery methods → must surface a specific toast ("No delivery option available for this city") and disable Confirm.

11. **order_items not re-validated.** Prices come from the cart (front-end). For COD/integrity, order-creation server-side should ideally re-read product prices from DB (or at least trust the cart but log). Flag as a hardening item; the schema has everything needed.

12. **No `updated_at` on customers** — minor; affects future audit but not required for this task.

## G. Final Expected Flow (target architecture)

```
Shopping Bag  (clearCart lives in UIContext)
   ↓  (router.push / Proceed to Checkout)
Checkout page  (CheckoutClient.tsx)
   ├─ Email field (optional, validate-if-filled)        ← frontend validation only
   ├─ City  → fetch zones/methods from DB (/api/shipping or cached)
   ├─ Delivery Method  → loaded from DB per city; live price (no hard-coding)
   ├─ Coupon Code → Apply  → POST /api/coupons/validate (server-side)
   ├─ Price Calculation (shared util):
   │      Subtotal(cart) + DeliveryFee − Discount = Final Total
   └─ Confirm Order
          │
          ▼  POST /api/checkout  (trusted, admin client, server-side)
          1. Validate input (Zod)
          2. Validate coupon (server-side, recompute discount)
          3. Resolve delivery (city→zone→method→fee, server-side)
          4. Compute totals (shared util)        ← single source of truth
          5. Find-or-Create Customer (by email; create guest if none)   ← admin client
          6. INSERT order (real order_number, delivery_method, coupon_code, ...)
          7. INSERT order_items
          8. Increment coupon usage (RPC)
          ↳ on success: return created order
          ↳ on failure: roll back / errorResponse, DO NOT create partial data
          │
          ├─ if FAILED → Toast(error), keep cart, stay on page
          └─ if SUCCESS → clearCart(), navigate to /order-confirmation?orderId=<id>
                                  (or populate localStorage from DB row as fallback)
Order Confirmation  (OrderConfirmationClient.tsx)
   ├─ read real order (DB via orderId, fallback to localStorage written from DB)
   └─ display order_number, customer, city/address, delivery method+fee,
      applied coupon + discount, itemized list, subtotal/discount/delivery/total
```

### Notes on "single source of truth"
- **One** pricing function (shared) used by: Checkout UI totals, `POST /api/checkout` total, the `orders` row, and Order Confirmation.
- **One** delivery-price source: DB `shipping_methods` per city's zone + per-method `free_shipping_threshold` (with global `store_settings.free_shipping_threshold` as the cross-cutting cap if desired).
- **One** customer-identity rule: `email` (UNIQUE) → find-or-update; no-email → new guest row; never duplicate by re-creating an existing email.

### Suggested verification before implementation (Phase 0)
- Confirm `increment_coupon_usage` RPC truly absent (grep done: **0 matches** in migrations) → add it.
- Confirm no INSERT policies exist for `orders`/`order_items`/`customers` for anon (schema read confirms) → use admin client for writes.
- Decide: `POST /api/checkout` (new) vs. fixing existing `POST /api/orders`. **Recommendation: add `/api/checkout`** and also patch `/api/orders` POST to admin client so the dashboard/admin path works too.
